# MachineQR

Smart Industrial Machine QR Code Management System.

Status: Phases 1 to 5 implemented (setup, database models, authentication and roles, machine management, QR codes).
Next: Phase 6 (machine digital profile with tabs).

## Requirements
- Python 3.11+
- Node.js 20+
- PostgreSQL 14+

## Backend setup
```
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # Windows: copy .env.example .env
```
Fill SECRET_KEY, JWT_SECRET_KEY and database URLs in `.env`.
Generate keys with: `python -c "import secrets; print(secrets.token_hex(32))"`

First-time database setup:
```
createdb machineqr
createdb machineqr_test
flask --app run db init
flask --app run db migrate -m "initial schema"
flask --app run db upgrade
flask --app run seed-roles
flask --app run create-admin
```

Already ran an earlier phase? Phase 3 adds two columns on `users` (failed_login_count, locked_until) and the
`token_blocklist` table. Run only:
```
flask --app run db migrate -m "auth lockout and token blocklist"
flask --app run db upgrade
```
Open the generated file in `migrations/versions/` and confirm it adds those two columns and the new table.

Run the API: `python run.py` (http://localhost:5000/api/health)

## Run tests
```
cd backend
pytest -v
```
Tests use the database in TEST_DATABASE_URL. Tables are created and dropped around every test, so never
point it at the real database.

## Frontend setup
```
cd frontend
npm install
npm run dev                     # http://localhost:5173
```
Vite proxies `/api` to `localhost:5000`. Sign in with the admin created by `create-admin`.

## Phase 3: what exists

API
- POST /api/auth/login, /refresh, /logout, /change-password; GET /api/auth/me
- GET/POST /api/users, GET/PATCH /api/users/<id>, POST /api/users/<id>/reset-password (admin only)

Security behaviour
- Passwords hashed (werkzeug), minimum 10 characters with letters and numbers
- Access token 30 minutes, refresh token 12 hours; logout revokes both
- 5 wrong passwords lock the account for 15 minutes; same error for unknown user and wrong password
- Role is read from the database on every request, so role changes and deactivation apply immediately
- Admin cannot deactivate or demote themselves
- Unknown JSON fields are rejected (no mass assignment)
- Login, lockout, user changes and password resets are written to audit_logs

Frontend
- Login (returns to the originally requested page, so a scanned QR link works after sign-in)
- Role-aware layout: sidebar on desktop, bottom navigation on mobile
- Admin Users page (search, role filter, pagination, create, edit, reset password)
- Profile page with change password

## Phase 4: what exists

No new database tables or columns (all machine tables came from Phase 2), so no new migration.
Install the new dependency: `pip install -r requirements.txt` (adds Pillow).

API
- GET /api/machines (search, status, department, category, is_active, pagination), GET /api/machines/options
- POST /api/machines (admin), GET/PATCH /api/machines/<code>
- PATCH /api/machines/<code>/status (admin, assigned technician)
- POST /api/machines/<code>/deactivate and /reactivate (admin; machines are never deleted)
- PUT /api/machines/<code>/assignments (admin)
- POST/GET/DELETE /api/machines/<code>/photo

Behaviour
- Machine ID (M-001, M-002, ...) is generated by the server and cannot be edited
- Specifications are stored per category; "Custom field" covers machine-specific values
- Access: admin sees all machines; technicians and operators see only machines assigned to them
- Operators get a reduced view (no PLC/HMI, specifications or technical notes)
- Photos are validated, re-encoded to JPEG (strips metadata), stored outside the web root and served only
  to users who may view the machine
- Machine detail lives at /machine/<code>, which is the URL the QR code will point to in Phase 5
- Create, update, status change, deactivate, assignment and photo changes are audited

## Phase 5: what exists

No new migration. New setting in `backend/.env`:
```
PUBLIC_BASE_URL=http://localhost:5173
```
This is the address that gets encoded into every QR code. For phone testing on your WiFi set it to your laptop,
for example `PUBLIC_BASE_URL=http://192.168.1.20:5173`, restart the backend, and open the frontend with
`npm run dev -- --host`. For real deployment use the final company address (HTTPS).

QR behaviour
- QR content is only `<PUBLIC_BASE_URL>/machine/M-001?v=1`. No machine data is inside the QR.
- Scanning only opens the login page if the person is not signed in; access rules still apply after login.
- Regenerate increases the QR version. Labels with an older version get an "Outdated QR label" message from the
  server (HTTP 410) instead of opening the machine. Plain links without `?v=` (for example from the machine list)
  keep working.
- Admin can download PNG, single label PDF (80 x 40 mm), print a label, or print an A4 sheet of all active
  machines (12 labels per page). Downloads are audited; the on-screen preview is not.
- Print PDFs at 100% scale (no "fit to page"), and scan a test label with a phone before printing a full batch.
- Labels use a built-in PDF font, so characters outside Latin-1 (for example Hindi names) print as "?". A Unicode
  font can be added later if needed.

Scanning
- Phone camera app: works on any address, opens the machine link in the browser.
- In-app scanner (Scan tab): browsers allow the camera only on HTTPS or localhost. Over plain http on the LAN
  the page falls back to the camera app or manual Machine ID entry.

## Known limits (to address later)
- Tokens are kept in localStorage. Acceptable for an internal network; revisit before internet exposure
  (httpOnly cookies, HTTPS, security headers) in Phase 12.
- No rate limiting by IP yet, only per-account lockout.
- Expired rows in token_blocklist are not cleaned up yet.
